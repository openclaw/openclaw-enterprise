# Milestone 1.3: PostgreSQL Persistence

## Problem and decision

Each deployment owns one PostgreSQL database and exactly one Installation;
Namespaces isolate resources within that database. This specification defines
the durable schema, migration workflow, repository boundary, authorization
recovery, and restart-safe queue for that ownership model.

Kevin requested “a spec for milestone2,” but the quoted persistence and queue
checklist belongs to
source Milestone 3.
Source Milestone 2
defines the initial OCC API and is already covered by
[`1.2-initial-occ-api.md`](1.2-initial-occ-api.md). Accordingly, this artifact
uses project subspec number `1.3` and implements source Milestone 3.

The selected design is:

- PostgreSQL is the only durable OCC persistence backend.
- Pin the latest stable production PostgreSQL release, currently PostgreSQL
  18.6, consistently across development, CI, and the production target.
- Persist one Installation per PostgreSQL database. Preserve its logical
  platform identity by projecting its ID into domain and API contracts instead
  of duplicating that ID on every business row.
- Use Namespace as the physical isolation boundary for Namespace-owned
  resources.
- A PostgreSQL adapter beside the existing OCC state store is internal
  infrastructure, not a Driver or a separate workspace package.
- Centralize typed current-state table definitions in one Drizzle ORM schema
  file. Drizzle Kit generates and applies checked-in, reviewable SQL
  migrations using its built-in migration history.
- Define PostgreSQL objects that the Drizzle schema DSL cannot fully express,
  including immutability triggers and grants, in handwritten custom migrations.
- `node-postgres` executes transaction-scoped repository work and the explicit
  `FOR UPDATE SKIP LOCKED` queue statements. Application services never receive
  a Drizzle database or `pg` client.
- Extend the existing `PlatformStateStore` into an asynchronous repository and
  unit-of-work contract. `PostgresPlatformState` implements the contract; the
  memory implementation remains an explicitly constructed test adapter.
- The controller queue is a PostgreSQL table with at-least-once claims, stable
  effect identity, leases, fencing tokens, persisted retry state, and stale
  claim recovery. Polling the table is the correctness and wake-up path.
- Queue claims serialize Namespace lifecycle operations per Namespace and Agent
  operations per Agent; Namespace readiness and deletion coordination use
  persisted Namespace state instead of blocking unrelated Agents.
- Implement and test the queue repository with a non-effectful claim harness.
  The harness neither starts a reconciliation worker nor dispatches an
  infrastructure Driver; source Milestone 5 owns those behaviors. Normal API
  requests continue to use the existing native IAM Driver.

[`docs/design.md`](../../../../docs/design.md)
defines platform ownership, authorization, isolation, immutable revisions,
active-revision semantics, failure behavior, and audit boundaries. This document
defines the implementation-local PostgreSQL schema and persistence mechanics;
it does not change the platform resource model.

## Scope

In scope:

- A local PostgreSQL service and explicit, validated connection configuration.
- The latest stable production PostgreSQL release, currently PostgreSQL 18.6,
  with identical pinned major and minor versions in local development, CI, and
  the production target; an older supported release requires a documented,
  evidence-backed compatibility exception.
- One canonical PostgreSQL schema, generated and custom SQL migrations applied
  through Drizzle Kit, clean-schema replay, and recovery.
- Durable Installation, Namespace, Agent, immutable admitted AgentRevision,
  native IAM, append-only audit, and controller-work tables; each Agent stores
  its one optional active revision directly.
- One-time Installation bootstrap and database enforcement for identity,
  Namespace ownership, scoped names, immutability, one-active-revision, queue
  lifecycle, and lease invariants.
- An asynchronous repository/unit-of-work port, PostgreSQL adapter, memory test
  adapter, and shared conformance suite.
- Initialized startup that reconstructs and selects the server-owned native IAM
  Driver from persisted authorization policy before accepting requests.
- Atomic resource + success audit + controller work transactions.
- Queue enqueue, claim, heartbeat, success, retry, terminal failure, dedupe, and
  stale-claim recovery APIs.
- Real-PostgreSQL concurrency, restart, migration, and catalog-level tests.

Out of scope:

- OAG evidence verification, trusted nondevelopment ingress, or production HTTP
  composition. Production startup remains disabled until OAG is delivered.
- A running controller loop, notification listeners, Driver dispatch,
  Kubernetes compute, gateway
  reconciliation, external effects, or effect-level exactly-once claims. Source
  Milestone 5 owns the controller; source Milestone 6 owns the complete revision
  deployment and activation workflow.
- A platform-selectable `DBDriver`, tenant-selected database, SQLite production
  support, or one portable schema across SQL dialects.
- Multiple Installations sharing one database, concurrent bootstrap, custom
  migration ledgers, or an OCC-owned migration runner.
- Importing, executing, migrating, or adapting anything under `legacy/`.
- Data retention, partitioning, cross-region replication, online destructive
  schema changes, or a tenant-direct database interface.

## PostgreSQL schema preview

Each database belongs to exactly one Installation. Bootstrap inserts that
Installation once; business tables neither repeat `installation_id` nor support
multiple Installations. The DDL defines the required schema and constraint
behavior. Implementations may change generated constraint names but must not
weaken keys, checks, indexes, triggers, or ownership tuples without revising
this specification.
