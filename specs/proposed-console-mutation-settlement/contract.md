# Console mutation settlement contract

This is a proposed extension to existing controller, OCC, IAM and State composition. It is not an installed API. The [decision overview](../proposed-console-mutation-settlement.md) describes the operator journey and scope.

## Settlement Protocol

The [lifecycle diagram](request-lifecycle.svg) and its [editable source](request-lifecycle.mmd) show the proposed ordering and competing admission.

The browser produces a random operation ID and retains the exact nonsecret intent before sending. The controller derives Installation and initiating principal from trusted admission. It binds the ID to Installation incarnation, Namespace, command kind, exact target kind, ID and incarnation, expected scope epoch, preconditions and a versioned digest of validated effect-bearing input. A plugin command cannot carry unrelated Agent edits. The controller recomputes the digest. Canonical version 1 sorts object keys, normalizes only unordered sets, preserves ordered arrays and distinguishes absent, null and default values according to the command schema. Server-allocated create-result IDs are reserved beside the digest and reused, not added retroactively to the client digest. Mismatched identity or input conflicts without changing the original or disclosing it to an unauthorized caller.

The following interfaces are proposals, not current routes or selected response schemas:

- `POST /namespaces/:namespaceId/mutation-operations` registers the ID, canonical version, kind, target/incarnation, expected epoch and typed request. The controller verifies the supplied digest against its own computation. A known committed reservation returns its bound epoch and allocated IDs or an authorized existing terminal outcome. An unknown reservation reply does not permit dispatch.
- Existing selected Agent PATCH and IAM Role/binding POST or DELETE routes would accept `X-OCE-Mutation-Operation` with that registered ID and the same command and preconditions. The header grants no authority. A known committed effect returns the existing safe resource result and its operation outcome.
- `POST /namespaces/:namespaceId/mutation-operations/:operationId/reconcile` takes the original descriptor. Under the same fence it returns an authorized `applied` receipt or commits a `prevented` tombstone, including for a known identity that has not arrived. These outcome names are proposed.
- `POST /namespaces/:namespaceId/mutation-operations/recover` accepts the target incarnation, logical-effect scope and observed epoch without an operation ID. Under the shared fence, authoritative retained records must discover pending and unacknowledged terminal predecessors. Current authorization permits disclosure of the original actor’s attributable safe outcome; an unauthorized or different principal receives no protected history, at most an authorized busy or conflict. Recovery also advances the epoch to fence unseen delayed registrations. It records an acknowledged boundary only after both discovery and epoch advancement succeed; an unknown reply remains blocked. A proposed `POST /namespaces/:namespaceId/mutation-operations/:operationId/acknowledge` records the currently authorized acknowledgment of each disclosed terminal result under the same fence, bound to its actor and logical-effect scope. The server refuses admission of an equivalent successor, including a plugin save with a different ID, until the predecessor is terminal and acknowledged. If authority or retained terminal knowledge cannot be recovered, the affected action remains unavailable.

[Main at 3995681](https://github.com/openclaw/openclaw-enterprise/blob/399568130cc5685f12959417423fdade7552a33f/packages/occ/src/state/platform-state.ts) provides `PlatformStateStore.read` and `transact` with `PlatformReadView` and `PlatformUnitOfWork` callbacks. This proposal requires an authority transaction that binds current IAM authorization and State mutation to the same transaction. The owners must establish a supported integration before enabling the feature; no adapter support is assumed.

A distinct State mutation-operation repository and scope fences extend `PlatformUnitOfWork`. The repository is a logical extension of original State, not a separate IAM engine or policy authority. [Agent access](https://github.com/openclaw/openclaw-enterprise/blob/98718e19787bb0139e0af1c5e63c4dad34c377fa/specs/36-agent-access.md) prohibits a second IAM engine, policy store, service, table, lease or account authority. Selected sharing and supported ordinary grant/remove writers must retain current administrator/account authority and target validity through physical COMMIT under selected IAM and original State, including revocation and target-deletion races; unsupported compositions remain unavailable. Real controller and limited-role PostgreSQL races must prove this. Enrollment currentness and native browser reauthorization for revoke remain separate from this RFC; reauthorization is not a settlement lease. **Open question:** State and IAM owners must select and prove physical storage that meets that decision and all settlement requirements; neither the logical repository nor the epoch fence selects a new table or lease. If this cannot be done, a proposed change requires an explicit human architectural and product decision before implementation. The existing `operations` repository holds controller lifecycle reconciliation, not these receipts. Each fence binds Installation incarnation, Namespace and exact target incarnation. All relevant Agent draft writers and deploy share the Agent scope. Selected grants also lock their logical-effect scope. Scopes are locked in canonical order. Each has a non-reused monotonic epoch and at most one pending reservation.

1. Registration compares the expected epoch under the scope lock, creates the unique pending slot and advances the epoch in one commit. No effect-bearing submit is sent before that commit is acknowledged. An unknown registration response is recovered or reconciled with the same identity.
2. Submit is admitted by its exact pending slot. Submit and reconciliation hold the same scope and operation locks through physical COMMIT. If submit wins, effect, attributable audit, immutable terminal receipt and epoch advancement commit together. If reconciliation wins, its committed tombstone prevents a later matching original attempt or registration. An unknown reconcile response remains pending.
3. A pending reservation blocks conflicting selected effects and same-target deploy across clients and principals. Every supported relevant write, deletion and successful deployment takes the same fence and advances the epoch, even for a no-op. If deploy wins before registration, the old registration is stale. If registration wins, deploy refuses. After a winning effect, a deploy carrying the old reviewed epoch also conflicts.

For example, an operator registers plugin operation O against Agent A at epoch 7. An acknowledged reservation advances the slot to 8. The selected PATCH carries O and the same plugin body. A lost response allows reconciliation of O, not another save. Once `applied` or `prevented` is known, the operator reloads and reviews before deploy. If deploy had advanced epoch 7 first, the delayed registration would conflict. These numbers illustrate ordering and are not defaults. This example has not been executed.

Ordinary reads, absence, timeout, denial or any unknown physical COMMIT do not establish nonexecution. They authorize neither replay, compensation nor a new equivalent effect. An exact-ID retry cannot re-execute an unknown effect. Recovery repeats reconciliation or establishes a durable boundary. PostgreSQL State owns COMMIT and propagates `PostgresCommitOutcomeUnknownError`. OCC does not run registered Driver rollback compensation for that error.

## Authority and Recovery

Current authentication and exact existing authorization apply to registration, submission, reconciliation, recovery and each disclosure. Plugin updates retain Agent update, Configuration read, and applicable removed or replacement Secret operate and ServiceAccount read checks. Policy writes retain Installation administer, Namespace read and exact binding-target checks. Authentication and authorization precede disclosure of existence, mismatch or history. An operation ID is not a capability. Denial does not establish that an earlier effect failed.

Original principal attribution survives reauthentication and account switches. A different principal cannot reuse the identity, clear another actor's slot or implicitly take over. If revocation or deletion prevents current or historical target authorization, keep the fence and disclose no protected result. Permanent loss of authority needs an explicit recovery decision. Unsupported authority, adapters or storage fail closed before effects.

Console retains the ID and typed nonsecret request before send. It stores no Secret values. Cross-tab coordination is advisory because the server fence is authoritative. Reload and navigation recover the same identity. Account switch separates journals and never transfers the original identity. Storage failure disables send. Storage clearing may erase even knowledge of a request still delayed before registration. An empty local journal or server listing is not settlement. Authorized ID-free recovery must discover retained unacknowledged terminal predecessors and pending slots, and advance the epoch under the shared fence to reject unseen delayed registrations. Epoch advancement does not reveal an already applied effect. An unknown recovery response remains blocked until a currently authorized follow-up establishes the durable boundary and required terminal knowledge.

For selected direct ensure-grant, proposed equivalence comprises Installation and Namespace, subject kind and ID, exact target and incarnation, canonical actions and every authority-affecting Role condition or restriction resolved under IAM authority locks. Role ID, operation ID, tab and actor do not define equivalence. Discovery and Agent or Secret grants have distinct scopes. Before adding a binding, participating writers inspect exact-equivalent direct bindings across Role IDs and return a currently authorized already-present result. Unclassifiable semantics make this path unavailable. This does not deduplicate arbitrary Roles or equate overlapping, inherited or group-derived grants. Role creation and binding creation remain separate outcomes. A removal records the exact binding and displays other remaining direct grants, without claiming total revocation. A later grant needs fresh intent after terminal removal. The server enforces predecessor terminal acknowledgment before admitting another equivalent effect across participating writers, even with another operation ID; a client acknowledgment alone is insufficient.

Keep immutable compact receipts and tombstones independently of target or principal deletion for as long as old requests can be admitted. No finite cleanup TTL is selected. Compaction requires a separately demonstrated non-resurrection boundary. Installation replacement must preserve the fence or use a distinct non-reused incarnation that rejects old requests. Epochs and incarnations prevent equal-value ABA from looking unchanged.

Each known Agent, Configuration, authentication, discovery, Role and binding result survives later failure. A saved object is not a receipt for an unknown step. Configuration and Slack Secret Driver effects are outside State atomicity. A State receipt cannot settle, replay, cancel, compensate or clean up those external effects. An uncertain adjacent external write remains visible and blocked under its owner.

## Reviewed Deployment

Guarded Console deploy compares the reviewed target incarnation and epoch, Agent plugins, harness authentication, execution mode and Backend, Configuration ID and generation, and displayed normalized repository bindings including effective defaults. Compare under actual admission locks before repository-credential admission and revision snapshot. A mismatch conflicts before effects and requires a fresh review. Server-selected policy freshness needs its own review. This comparison is distinct from settling a save and from runtime readiness.

At [main 3995681](https://github.com/openclaw/openclaw-enterprise/blob/399568130cc5685f12959417423fdade7552a33f/apps/controller/src/console/agents/create.mjs), Agent creation now selects a model credential Secret and still calls Secret-access binding after Agent creation. Those independently partial outcomes remain in scope; this change does not provide settlement.

The repository-binding comparison above is required to reject a changed binding before credential admission. Its implementation and qualification remain open; a fixture alone cannot prove PostgreSQL, live-provider, ABA or unknown-save settlement behavior.

## Implementation

1. State and IAM owners select the authority transaction before ordinary transaction entry. The integration must acquire authority before entering an ordinary transaction; nested entry must not bypass authority or the shared fence. Proposed lock order is Installation authority, auth/session/key and policy barriers, sorted scope fences, operation identity, Namespace, then sorted affected Agent, Configuration and IAM resource locks, held through COMMIT. Validate the actual lock graph including Agent create, provision, delete and finalization plus identity, session and policy invalidators.
2. Add the State repository and controller registration, attachment, reconciliation and recovery interfaces. Keep existing selected mutation routes. Every supported relevant writer and invalidator must take the same fence or remain unavailable. Preserve secure memory, service-key and legacy paths. Drain or fence old identity-free in-flight code before enabling the flow. A new-version ID cannot bind an old request retrospectively. Permanent support removal needs human product authority.
3. Adopt PR 434 plugin save and guarded deploy. Bodyless deploy retains latest-draft semantics but must still refuse a pending scope and advance the epoch. Only guarded deploy promises comparison with reviewed facts. Then adopt PR 384 Namespace discovery and Agent sharing, Role and binding creation and selected deletions, and Secret-access callers in saved-Agent creation, detail, authentication, channels and credentials. Plugin-first is sequencing, not completion. Integrate the corrected origin-security supplier with independent review. Resolve the sharing migration against the final journal and OIDC supplier, then prove fresh and upgrade databases.

## Acceptance

Use the actual controller and migrated disposable PostgreSQL with the limited application role. An owned fault proxy must send the original request once and delay it before admission and before COMMIT. Exercise each winner, both deploy races, lost reservation, mutation, reconciliation and recovery replies, exact retries, mismatched actor, Installation, Namespace, incarnation, payload and preconditions. Verify durable effect, audit, receipt and fence, and show ordinary reads cannot release uncertainty. Test current authorization, revocation and non-disclosure, all supported writers and invalidators, no-op and ABA changes, deletion, retention and old-request rejection. Prove actual role privilege denials and run guard-removed negative controls. Isolate CI fixtures and report counts, failures and skips.

A real browser must exercise cross-tab, reload, navigation, account switch, storage failure and clearing, pending recovery, independently partial Agent, Configuration, authentication, discovery, Role and binding outcomes, and stale reviewed repository bindings before credentials. Test guarded deployment on both sides of the admission lock. A separate real PostgreSQL control must expire the session after the final check and across physical COMMIT. None of these composed tests is claimed by this RFC.

In a real browser with the actual controller and the relevant owned Driver or fixture, induce an uncertain Configuration or Slack Secret Driver save, then obtain a valid selected plugin or IAM State receipt. Verify that the external outcome remains separately visible and blocked under the Configuration or Secret Driver owner, with no replay, compensation or overall-readiness claim. Name that owner and the evidence needed to resolve the external outcome, or explicitly refuse unresolved recovery. These external effects remain outside State atomicity.

For both the actual controller/migrated PostgreSQL and a real browser, clear storage after an effect and terminal receipt commit but the reply is lost; require authorized discovery, attribution, server-recorded acknowledgment and refusal of an equivalent successor with a different ID before acknowledgment. Separately delay an unseen registration, clear storage, recover and advance the epoch, and prove the old registration is rejected. Exercise denied and revoked disclosure, a different principal and unrecoverable terminal knowledge; the action stays unavailable without disclosing protected history. A removed acknowledgment or epoch guard must make the corresponding control fail.

In both environments race distinct operation IDs and equivalent permissions under different Role IDs across every participating Console and supported non-Console writer. Lose or delay Role and binding replies, retain partial outcomes, then settle and remove or revoke a selected binding. Assert no duplicate direct authority and preserve separately legitimate Roles, other direct and discovery grants; removal must not claim total revocation. Test a removed equivalence guard as a failing control and report selected-case counts, failures and skips.

Qualification must resolve session expiry, validate the actual Agent/IAM lock graph, preserve memory and service-key compatibility, isolate CI fixtures and verify application-role privileges. Source review, CI, installed behavior, live-provider qualification, human acceptance and publication remain separate.

## Open Decisions

Strict session validity at physical PostgreSQL COMMIT is required. IAM, State and session owners must resolve its enforcement and feasibility and demonstrate an enforcing guarantee in real PostgreSQL with the limited role. The feature remains unavailable until that guarantee is demonstrably enforceable. Locks, a final timestamp check and ordinary statement timeouts cannot stop wall-clock expiry or prove this guarantee. Any proposed relaxation must be identified as such and requires explicit human product authority. A separate audit-publication expiry question also remains open.

Owners must decide recovery after permanent loss of initiating authority without changing attribution or silently granting administrator takeover. The proposed direct-grant equivalence and participating legacy writers require IAM and product acceptance. Unsupported or unresolved cases remain unavailable, rather than receiving a weaker guarantee by default.
