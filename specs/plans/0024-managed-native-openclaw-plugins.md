# Implementation plan: OCE-managed native OpenClaw plugins

- **ID:** RFC-0024
- **Delivery status:** Planned
- **Owner:** OCE Plugin, Credential, Sandbox, Compute, Console, and runtime maintainers
- **Authority:** [OCE-managed native OpenClaw plugins](../rfcs/0024-managed-native-openclaw-plugins.md)
- **Source baseline:** `000aa1d6b80103d7cccac9598ea628deee389098`

## Outcome and scope

An administrator can select a reviewed integration for an OpenClaw Agent, connect an authorized identity, choose supported services and action settings, and deploy the Agent. For Google, OpenClaw prepares the selected skill for a delegated turn, and the Harness worker runs the reviewed [gog](https://github.com/openclaw/gogcli) executable using the connection binding. P0 delivers a working managed plugin lifecycle and a representative Google workflow, including translation of supported plugin actions into credential authorization rules and enforcement of the effective binding policy for both gog and custom code. Broader coverage of the pinned gog release remains a product goal.

The [PluginDriver contract](../../docs/reference/drivers/plugin.md) owns catalog and policy validation; OpenClaw Control Plane (OCC) owns Agent selections and revisions, and Compute owns runtime preparation. OpenClaw runtime maintainers work with the [credential source](../../docs/reference/credential-sources.md) and [Credential Proxy and Sandbox](https://github.com/openclaw/openclaw-enterprise/blob/7d472f3f7d3b5104deb7e18ae7a2627ce1da0f91/specs/rfcs/0023-egress-proxy-credential-lifecycle/security.md#L126-L138) owners to deliver the selected connection and effective credential policy through Compute to the admitted runtime. OpenShell remains an implementation of these contracts. The Credential Driver owns credential authorization policy; the selected Credential Proxy enforces it before injection, and Sandbox prevents direct egress. Console exposes editable, schema-validated JSON policy and the effective grants for each Agent binding.

**P0 release requirement:** Every admitted credentialed route must pass mandatory, fail-closed authorization against the execution's effective binding policy before credential injection. The same policy applies to gog and model-executed custom code. Provider-granted OAuth scopes remain an upper bound; a destination allowlist or injectable placeholder alone does not authorize an operation. Qualify the selected egress composition against the [Credential Proxy release requirements](https://github.com/openclaw/openclaw-enterprise/blob/7d472f3f7d3b5104deb7e18ae7a2627ce1da0f91/specs/rfcs/0023-egress-proxy-credential-lifecycle/online-authorization.md#release-requirements-for-mandatory-online-authorization).

## Delivery steps

Each numbered step is a logical PR scope corresponding to the RFC. Steps 1–12 form P0; workstreams may proceed in parallel where dependencies allow, but final qualification in step 12 depends on the preceding P0 work. Steps 13–16 cover later work and separate investigations.

### P0: working managed OpenClaw plugins

1. **Catalog and Agent binding.** Extend the owning Plugin Driver paths to describe the reviewed Google integration, skill, compatible runtime artifact, connection requirements, and supported OpenClaw placement. Extend Agent selection and deployment admission to bind the exact catalog release, reviewed metadata, connection reference, chosen services, action settings, and credential destination policy to an immutable Agent revision. Require authority for the Agent and selected connection, reject incompatible placement, and keep credential values out of selections and revisions.
2. **OAuth connection lifecycle.** Let an operator manage multiple reusable OAuth client configurations in a Namespace, each backed by a Secret for the client ID and client secret. OCE initiates consent before Agent deployment. A trusted OCE connection handler completes the callback and code exchange, then hands the refresh grant and initial access token to the selected credential lifecycle. Its admitted owner holds the only durable copy of the refresh grant and performs subsequent refresh; mark the connection ready only after handoff succeeds and the initial token passes admission and eligibility checks. Record observed granted scopes separately from requested scopes. Resolve uncertain exchange outcomes without replaying rotating refresh tokens. Related: [#3098](https://github.com/openclaw/openclaw-enterprise/pull/3098) implements the personal Agent OAuth backend proposed in [#3068](https://github.com/openclaw/openclaw-enterprise/pull/3068). Its Installation-owned templates, OpenShell custody of client secrets, and owner-only Agents need alignment. Its exchange retains only the refresh token, so initial-token handoff and observed granted scopes remain work.
3. **Console selection.** Extend the Agent Plugins workflow to select a saved connection or create one using a Google OAuth application. For a new connection, group the scope inventory from step 6 by product and initialize selections from the chosen products and read-only or all supported actions. Allow product-wide and individual selection, plus custom scope entry; send the final scope set in the Google authorization request. Before deployment, show observed grant scopes, unavailable plugin actions, provider prerequisites, and the administrator-approved destination, operation, and input restrictions required for custom scopes. Distinguish provider scopes from the effective credential policy, which governs both gog and custom code in P0; selecting narrower plugin settings does not narrow a broader saved Google grant. Related: [#3175](https://github.com/openclaw/openclaw-enterprise/pull/3175) adds template management and consent for personal Agents, with requested scopes fixed by the template. Plugin-driven scope selection and credential readiness before the first deployment remain work.
4. **Execution binding and worker propagation.** Admit a fresh execution-specific credential grant, binding, and routes from the Agent revision. Have Compute configure the execution's proxy plan through `CredentialProxyDriver`, then have Sandbox apply and attest the returned wiring. Give the dedicated OpenClaw worker its admitted placeholder and required proxy and certificate authority settings. Keep model and platform credentials isolated. Replacement workers must reapply the saved policy with a fresh execution binding. Request authorization uses the authenticated execution and its credential binding for both gog and custom code; a caller-supplied plugin name or possession of a placeholder is insufficient.
5. **Runtime packaging and skill.** Pin and verify gog in the dedicated Harness worker image. Project the admitted skill selection into OpenClaw’s existing [Gateway skill-context preparation](https://github.com/openclaw/openclaw/blob/f8386bc7df0a6c9eda7a28ae81943c5c06a414ff/src/gateway/worker-environments/worker-turn-prompt.ts#L118-L133) and [delegated worker-turn path](https://github.com/openclaw/openclaw/blob/f8386bc7df0a6c9eda7a28ae81943c5c06a414ff/src/gateway/worker-environments/worker-turn-execution.ts#L565-L586); qualify that the worker receives the prompt and resources needed to use the selected skill. This does not load a Google extension into the Gateway. Preserve an Agent-owned durable workspace for generated scripts and artifacts, with an index of their purpose, arguments, and last validation. Use the applicable [workspace storage](../../docs/reference/drivers/kubernetes-compute/storage-and-credentials.md); a replacement pod must preserve same-Agent reuse and cross-Agent isolation.
6. **Google service and scope inventory.** Publish a product-grouped OAuth scope inventory based on the pinned gog release and provider metadata. Associate supported plugin actions with the scopes, credential modes, and identity prerequisites they require, and identify gaps in product coverage. Full gog coverage remains a product goal, but exhaustive operation coverage and additional provider-specific credential modes do not gate P0. Step 9 owns the reviewed, versioned translation needed to enforce each supported action in P0.
7. **Credential modes and destinations.** Support the credential mode needed for the initial Google workflow and bind the connection to reviewed API destinations without creating multiple refresh owners. Apply the execution binding's effective policy before credential injection. A custom OAuth scope requires an administrator-approved endpoint and operation allowlist, including enforceable input restrictions, before activation. The personal Agent backend binds one host, port, and path pattern, but releases the credential for every HTTP method to configured tool binaries; it does not enforce plugin actions or inputs. Add service-account and other provider-specific modes as broader coverage is developed.
8. **Credential authorization policy and Agent binding.** Define the Credential Driver’s schema and APIs for native credential policy and the effective authorization policy for each Agent binding. Keep configured plugin choices identifiable for the plugin UI. Resolve how native policy and plugin-derived contributions relate, including composition, precedence, ownership, persistence, and changes to running executions; merging is a candidate, not a settled design. Keep one Agent’s binding isolated from another Agent using the same connection.
9. **Google action-to-policy translation.** Use the reviewed service and scope inventory from step 6 to translate supported Google actions into versioned, attributable request constraints for the selected binding. Make generated contributions traceable to the plugin and action so they can be withdrawn without silently changing independent credential policy. An action without a translator receives no automatic grant; administrator-authored rules require the same validation and enforceable matcher. These are credential authorization rules, not Harness action permissions.
10. **Credential policy Console.** Build the credential-policy editing and effective-grant views on the APIs from step 8. Let administrators edit schema-validated authorization configuration and see each Agent binding’s effective policy, including any grant that remains when an action is disabled. Keep plugin choices visible in the Agent plugin UI and distinguish saved configuration from policy confirmed applied at the enforcement boundary.
11. **Protected request authorization.** Integrate the selected Credential Proxy and Sandbox composition with the binding policy and qualify it against the Credential Proxy release requirements. Match the actual origin, normalized path, method, query constraints, and relevant body fields before injection; deny requests that cannot be authorized, block direct egress, and ensure redirects, batches, and downstream mutation cannot broaden authority. Record the policy version, matched rule, and decision without credentials or private request data.
12. **Ordinary deployment and qualification.** Integrate the preceding P0 work through Agent deployment, readiness, replacement, and retirement. Withdraw the binding and its policy contribution when the selection is removed without affecting other Agents using the same connection. Run the Verification section against the deployed Google integration. Update the owning Plugin, Credential, Sandbox, Compute, Console, and OpenClaw runtime documentation in the implementation PRs.

### Later work and separate investigations

13. **ClawHub discovery.** Add search and details through the Plugin Driver. Show compatibility and admission status, including unsupported capability classes. Registry discovery grants no installation or execution authority.
14. **ClawHub release lifecycle.** Admit an exact reviewed release and its complete capability and dependency set; bind it to the Agent revision and verify its artifact before Compute materializes it. Release updates require a new review and Agent revision. Preserve restart from an already-admitted artifact when the registry is unavailable.
15. **Separate MCP discovery and enforcement investigation.** No new managed remote MCP integration is required for native plugins. If additional discovery or per-tool control is needed, check whether the existing path covers credentialed discovery and request-boundary enforcement, including multiplexed routes and tool-name or argument constraints. Discovery grants no authority. Scope separate implementation only for a confirmed gap.
16. **Deployed credential access visibility.** Trace Agent revision bindings through credential source configuration, Credential Proxy configuration (including OpenShell provider profiles when selected), and Sandbox-applied wiring and policy. Investigate an authorized read-only Agent API and Console view of source references, placeholder variable names, injection destinations, and enforced operation limits. Distinguish configured from confirmed applied policy and network access from credential injection; exclude credential and placeholder values. The P0 credential-policy view in step 10 does not depend on this broader inventory. Validate displayed access against allowed and denied requests, redeployment, and shared connections.

## Verification

For P0, exercise ordinary Console-to-Agent deployment on a supported Kubernetes stack with the selected Credential Proxy and Sandbox composition and an authorized test identity. Verify that the Google authorization request matches the selected scopes, the worker receives the placeholder and required trust settings, and an allowed action succeeds through both gog and custom code. An action excluded by the effective binding policy must be denied through both paths with no new upstream request. Check refusal at an unadmitted destination, grant mismatch, unauthorized connection selection, refresh failure, and an Agent without the selection. Verify that a custom scope cannot activate with an endpoint binding alone or without enforceable, administrator-approved operation and input restrictions. At an approved destination, verify that an allowed operation with permitted inputs succeeds, while a disallowed operation and an allowed operation with disallowed inputs are each denied before credential injection. Keep credential values out of evidence.

Replace the worker and start a fresh conversation to verify that the same Agent retains its workspace, reuses the selected integration, and reapplies saved policy through a fresh execution binding. Confirm fresh-request denial after removal or revocation withdraws the Agent's binding and policy contribution, while another Agent's access to the shared connection remains unchanged. Withdrawal cannot recall a request already authorized. Record the tested Agent revision, actual runtime versions, policy version, matched rule and decision, and sanitized provider-result evidence; distinguish configured policy from confirmed applied enforcement.

P0 enforcement qualification must also exercise disallowed inputs on the same URL, mixed allowed/denied batches with no upstream forwarding, malformed or unsupported bodies, missing translators with no automatic grant, validated manual rules, overlapping generated/manual/provider grants, credential aliases, alternate credentialed routes, and shared-connection binding isolation. Exercise nested processes and persistent terminals where supported. Verify mandatory authorization on every admitted credentialed route, denial when authorization is unavailable, blocked direct egress, and reauthorization for redirects or operation changes. Verify that disabling an action withdraws the plugin-owned contribution without silently changing independent credential policy, and show any remaining effective grant. Test policy changes to running executions according to the propagation semantics chosen in step 8; do not report saved policy as applied before enforcement confirms it. All of these checks are P0 release gates.

Report the reviewed plugin release, supported products and scopes, tested provider prerequisites, live allowed/denied results for gog and custom code, and confirmed applied credential policy. Track broader gog action and credential-mode coverage separately. Later ClawHub delivery needs its own installed-artifact and allowed/denied request proof. The MCP investigation should report whether a concrete gap exists; define implementation scope and qualification only if additional work is needed. Request-time approvals, reviewer routing, elicitation, additional providers, and multiple end-user accounts per Agent remain later work. Public schema caching by API version is a later performance optimization unless needed for the initial workflow; any public schema retrieval uses no credential.
