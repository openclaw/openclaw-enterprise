# Implementation plan: Managed OpenClaw plugins

- **ID:** RFC-0029
- **Delivery status:** In progress
- **Authority:** [Managed OpenClaw plugins](../rfcs/0029-managed-openclaw-plugins.md)
- **Source audit:** `18041cc84aa0292ed20b0d40e90ec9538a1bacc4` on 2026-11-05; source and PR status, not a new runtime qualification.

## Outcome

An operator configures a reusable account, selects reviewed CLI or hosted MCP plugins, selects MCP tools where applicable, and deploys an OpenClaw Agent. Native calls and admitted scripts obey the credential binding's request policy. Account renewal, worker replacement, plugin removal, and independent credential attachments follow their owning lifecycle.

The RFC owns the design and boundaries. This plan records delivery and verification. Existing merged work is the baseline; open PRs remain incomplete until their supported workflow is qualified.

## P0: complete the connected-account workflow

These are logical PR scopes, ordered by actual dependencies. The active sequence is **#4668 → #4671 → #4673 → deployed qualification**. Runtime and tool-selection prerequisites above have merged.

1. **Template and OAuth client administration — [#4668](https://github.com/openclaw/openclaw-enterprise/pull/4668), open.** Provide Installation-wide or Namespace-scoped templates, approved issuer/resource/destination settings, scope limits, and multiple client registrations. Support manual setup or MCP metadata discovery. Console owns the management workflow; OCC owns authorization and versioning; the selected Refresh Driver owns private client registration material. Verify create, select, rotate, and cross-Namespace refusal through the real Console/API. Automated provider-side dynamic client registration remains separate.
2. **Saved accounts and renewal — [#4671](https://github.com/openclaw/openclaw-enterprise/pull/4671), open; depends on 1.** Complete browser consent, save the Namespace account, record requested and granted scopes, and hand the grant to Token Service. Refresh uses the current secret of the pinned client registration. Verify account reuse, client-secret rotation without fresh consent, scope narrowing, provider rejection, and private-store failure through the owning HTTP and persistence paths. Preserve one refresh owner.
3. **Agent grants, plugin slots, and delivery — [#4673](https://github.com/openclaw/openclaw-enterprise/pull/4673), open; depends on 2.** Bind named release slots to compatible accounts; support Connect from Plugins and reauthorization for another protected resource. Recheck the slot and caller at callback. Read warmed access tokens for MCP discovery, deliver expiring tokens, renew sender presentations, and withdraw only the affected Agent grant on explicit account detach. Extend Google delivery to multiple approved service routes and approved script executables under the same guard. Verify shared-account isolation, concurrent slot changes, detach, and independent attachments. The bundled releases each currently declare one account; a two-slot fixture does not establish arbitrary multi-account UI support for every plugin.
4. **Deployment packaging and complete workflow proof — remaining; depends on 1–3.** Qualify the account flow through an ordinary OCE deployment, including API egress for discovery/code exchange and OCC background worker/Token Service egress for renewal. Audit useful packaging from [#3152](https://github.com/openclaw/openclaw-enterprise/pull/3152); its API-only OAuth egress is not sufficient proof for Token Service refresh. Run the checks below on the final image and record Console evidence. Update the owning references, guides, and flows with the implementation that ships.

The new connection stack is independent of [#3098](https://github.com/openclaw/openclaw-enterprise/pull/3098). That PR and [#3175](https://github.com/openclaw/openclaw-enterprise/pull/3175) contain overlapping backend/Console work; reconcile them with their owners rather than merging duplicate implementations. [#4008](https://github.com/openclaw/openclaw-enterprise/pull/4008) is the earlier template branch. The closed credential-ownership stack #3806/#3808/#3811/#3812 is not a prerequisite; retiring its legacy interfaces is a separate architectural change.

## Verification

P0 qualification uses a real authorized account and the normal Console flow on an OCE-deployed Agent. Controlled tests establish their stated boundaries; the open account stack's Keycloak and recorded OpenShell transport cases do not substitute for this deployed MCP/Google proof.

- **Connect and deploy.** Create/select a template and OAuth client, consent, choose a saved account from a plugin slot, discover/select MCP tools where applicable, and deploy. Verify the actual selected resource, scopes, runtime image, and saved Agent revision. No secret appears in Console responses, artifacts, model context, or logs.
- **MCP allow and deny.** With a grant that offers both allowed and disabled tools, verify an actual Agent tool result and an equivalent admitted script call. Attempt the disabled upstream tool directly and verify zero upstream calls. Change the selection in Console, redeploy, and repeat. Exercise reconnect and expired-token renewal through the same credential owner.
- **Google allow and deny.** Verify a supported operation through gog and an approved direct-HTTP script. Deny an operation outside the binding, including a disallowed parameter on an otherwise allowed route. Use a sufficiently broad provider grant so provider scope rejection cannot masquerade as OCE enforcement.
- **Lifecycle and isolation.** Replace the Harness, start a fresh conversation, and verify selected artifacts, policy, and workspace reuse. Detach an account from one Agent and verify new requests fail after confirmed withdrawal while another authorized Agent/attachment remains usable. Removing a plugin must preserve independently retained credential access and worker recovery. Exercise account refresh failure and scope narrowing.
- **Policy boundaries.** Refuse unapproved destinations, unsupported operations, overlapping MCP routes, malformed requests, and incompatible Sandbox/Proxy combinations. Verify account changes invalidate stale discovery and credential material remains outside Gateway tool metadata.

Record sanitized request counts/results, the tested release and policy, actual runtime versions, and the final PR head. Keep a short Console recording beside the implementation PR. Broad Google coverage, arbitrary MCP argument constraints, new providers, and alternative enforcement adapters require their own checks as they are added.
