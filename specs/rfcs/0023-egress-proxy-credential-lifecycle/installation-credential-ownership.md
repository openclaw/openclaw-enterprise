# Select one credential owner per Installation

This proposed amendment changes the v1 delivery decision in RFC-0023 and the OAuth custody decision in RFC-0027. An Installation selects a TokenService Driver. OCC owns source metadata, Agent bindings and IAM. The selected Driver owns usable values, issuer keys and refresh grants. OCC's implementation uses SecretDriver. OpenShell's implementation uses the configured Gateway and the Workspace established through the existing Namespace lifecycle. One registration can provide several capabilities. A change to Installation selection cannot transfer custody of a registered source.

## Register and use a source

OCC allocates the scoped source identity before sending write-only material and lifecycle settings to the selected owner. After success it records the selected Driver ID and any nonsecret backend reference. Reads of source metadata never return material. The owner can replace material or lifecycle settings, resolve the authorized usable credential with optional version and expiry metadata, start refresh and report its status. Push delivery requires a version. OCC resolves only after authorizing the consumer. Console discovery uses the authorized value directly. Compute delivers Gateway startup credentials at deployment. A Gateway must restart to pick up a replacement.

At deployment the deployer and Agent service principal both need operate permission on each bound source. The Agent needs no grant on the underlying Secret. Installation OAuth client registrations have their own identity and metadata. Their secrets remain with the owner and cannot be bound to an Agent. The issuer retains GitHub App keys, and OCC's Git repository and branch authorization applies with either owner.

OCC withdraws bindings before deleting owner material. If registration has an uncertain outcome, a supporting owner can remove material by the allocated identity even when OCC received no backend reference. The protocol requires no background repair operation.

## Configure delivery

For OCC-owned material, the proxy initializes a shared delivery resource from the current version on first use. It keys the resource by Namespace and source. Each deployment binding has its own placeholder and injection rule. The proxy tracks the delivery version requested at initialization or on the latest push to that resource. A push must update that resource even if it currently has no serving copies. Before acknowledging, the proxy observes that every serving copy for the source can use the pushed version. If no delivery resource exists, the push succeeds without creating one. The proxy must coordinate first use and changes in serving copies with updates.

A failed push leaves the new source value authoritative. OCC reports a sanitized failure and an authorized administrator can push again. Refresh status describes issuance. A subsequent deployment checks the existing delivery resource without repairing it. Detecting a source update that never reached the proxy is deferred; administrators recover failed delivery by pushing again.

For OpenShell-owned material the embedded proxy attaches the registered native provider after checking its backend and Workspace. Missing or incompatible references fail preparation. OpenShell manages native renewal. An external proxy cannot deliver these sources in v1. The embedded proxy requires an OpenShell Sandbox. A standalone proxy requires an OCC owner and a Sandbox that enforces its routing. Withdrawing a deployment preserves shared resources still in use. The proxy can delete unused delivery resources. Only TokenService deletes authoritative material.

## Prepare an Agent revision

PluginDriver describes the selected tools, required artifacts, workload and network requirements, and credentials for each named connection. OCC admits source references. Compute coordinates tool preparation with the runtime. SandboxDriver provisions an execution target and applies process restrictions, network policy and any mandatory proxy routing. CredentialProxyDriver configures injection per binding and returns projection descriptors. The runtime supplies fresh placeholders when the Harness starts.

For a hosted Codex App, OCC admits the selected plugin and its remote identity, connector IDs and required bundle content from the authenticated release for the Agent's Harness account and workspace. It verifies that the selected connectors and tool overrides are available to that account, binds the record to the revision and passes it to PluginDriver. A default-only selection retains its connector IDs even with no tool overrides. Missing or incompatible admission fails preparation. The operator can redeploy a new revision.

PluginDriver emits one tool entry per admitted connector ID. The Harness disables unselected apps and applies each selected app's enablement, tool defaults and scoped overrides. It resolves overrides against that connector's authenticated tool inventory and rejects unknown, unowned or ambiguous tools and conflicting policies for a shared connector. An explicit default for tool enablement bypasses Codex's destructive-tool filter. Reject a policy that sets both. This path requires no marketplace lookup, installation or downloaded skill.

When the runtime needs an artifact, it checks the bytes it consumes against the reviewed digest. Google has separate pins for the Gateway skill and each platform's Harness binary. Slack pins the MCP server manifest and selects its named server. The release metadata digest identifies the declaration. A Codex plugin that also needs bundled content such as a skill declares a separate marketplace selection. The marketplace name and native plugin ID identify the selection before lookup. Version selection and verification for that content remain open.

A reviewed plugin slot supplies its environment name and credential presentation. For the Google and Slack slots, `bearer` permits the placeholder only in the HTTP Authorization header with the Bearer scheme. Compute carries that projection into the proxy binding. Each model binding must use its reviewed provider profile. OpenAI API keys use Bearer authorization. Anthropic API keys use the raw placeholder in the `x-api-key` header. A bearer-only delivery implementation must reject the latter. Repository bindings retain their admitted Git delivery profile and its operation-specific authorization. The proxy rejects missing, incompatible or unsupported presentations. Multiple connections need distinct projections and a plugin-supported way to select an account per invocation. Reject two bindings that would overwrite the same fixed environment input.

Network access and injection each match the executable, destination and ports, with HTTP or MCP restrictions where required. A credentialless plugin can request network access alone. An allowed connection cannot use a placeholder outside its binding's injection rules. Admission enforces the Installation ceiling. Preparation fails if overlapping rules weaken a restriction, the target can bypass required routing, or either enforcing Driver cannot represent its policy. Preserve any additional request authorization required by a binding.

OCC derives each binding's injection destinations from its admitted source and intersects them with the plugin's requested endpoints. An unconnected requirement grants no credential access. For a saved OAuth connection, use the current compatible template's manual destinations or the consented MCP recipient, as specified in RFC-0027. Network-only discovery can reach an admitted endpoint without receiving a credential, including a different path on the same host.

The provider enforces the actual OAuth scopes and permissions of the credential. The proposed delivery contract does not use a plugin-specific API or scope evaluator. The existing Google runtime guard remains until its Driver adopts this contract. A permitted request can fail at the provider for insufficient permissions; the Harness receives that error. If the credential has broader permissions than OCE metadata indicates, the provider can permit them within the admitted endpoint. Static HTTP restrictions can select an exact path or a path subtree and a method; MCP restrictions can select a method and tool.

1. Compute sends the logical revision identity and admitted policies to the proxy. A standalone proxy can return a public trust bundle and mandatory routes for Sandbox creation. Its signing key stays with the proxy. If creation fails, Compute can release unbound proxy resources by revision identity.
2. The Sandbox stages a target with credential-using execution held. Subsequent calls identify its exact incarnation. For OpenShell, attach the providers to the staged target, then apply the combined network and injection configuration with the current native resource version. On conflict, read the current version and recompose the policy.
3. Compute observes network and proxy readiness for the same desired configuration after the final write. For OpenShell, the submitted base policy must be active and each provider ready for the current effective policy. A pending snapshot mismatch keeps the Harness held. Each pushed binding needs a serving copy. The proxy observes its expected delivery version on every copy serving that binding on this target, without issuing credentials, sending an upstream user request, reloading or repairing the resource. A healthy peer or successful reload can coexist with a stale copy. Missing evidence keeps the Harness held. Reject push delivery if the proxy cannot observe effective versions.
4. The runtime prepares fresh projections for the held Harness. A standalone proxy can issue the placeholder. On OpenShell a fresh supervisor-mediated launch can receive the installed placeholder. The Sandbox authenticates the held launcher and identifies the configuration, sandbox incarnation, process instance and fresh startup challenge. After network and proxy readiness, the runtime hands the reviewed placeholders to that exact startup. The launcher must acknowledge their installation. A replacement must refuse a handoff or release addressed to the previous startup. Compute rechecks tool, network, proxy and workload readiness before signing release for that startup. After release, the Harness can begin credential-using work with the installed projections. Compute confirms activation through authenticated serving status for that instance.

After a lost reply, the next worker observes the current instance before acting. It can adopt a serving instance or recheck readiness and release a held one. Preparation must be idempotent. An OpenShell exec request ID cannot recover a long-running process across disconnects. The current protected launcher captures credential inputs before release. It needs an authenticated, startup-bound placeholder handoff before this flow can work. The transport and worker-loss recovery still need implementation and qualification.

A rejected withdrawal leaves the old policy in force and cannot count as completion. Enforce executable and port restrictions in the Sandbox if the proxy cannot distinguish them, or reject the policy. Reject stale or misplaced placeholders even on an allowed network request. Request-time sandbox pulls and automatic push recovery are deferred.

## Contract entry points

- [TokenServiceDriver](../../../packages/contracts/src/drivers/token-service/index.ts) owns the six source lifecycle operations. OCC validates and persists its registration and supplies the recorded reference to trusted consumers. Client-registration material has a separate Installation identity and no delivery binding.
- [Plugin deployment](../../../packages/contracts/src/drivers/plugin/deployment.ts) describes one plugin at a time. Tool IDs connect each named credential to its consumer and reviewed request requirements. An installed plugin may declare a credential requirement with zero connected accounts.
- The historical [Sandbox deployment contract](https://github.com/openclaw/openclaw-enterprise/blob/840e8ac0044e0d803f7975632ce4d58e3c9f9006/packages/contracts/src/drivers/sandbox/deployment.ts) and [proxy deployment](../../../packages/contracts/src/drivers/credential-proxy/index.ts) shared [deployment references and policies](../../../packages/contracts/src/credential-deployment.ts). The fresh-start amendment below replaces the Sandbox contract with direct Driver operations.

## Qualification

Exercise OCC ownership with embedded and standalone proxies, and native ownership with the embedded proxy and no SecretDriver. Verify first use after a source update, sharing across Agents with different request policies, denied injection on an allowed connection, failed push and manual recovery, withdrawal and sandbox replacement. Verify native OAuth and Git issuance, shared client-secret rotation, Console export and Gateway restart with the selected owner. These are release requirements. The amendment alone establishes no runtime support.

## Amendment: start a fresh Harness at activation

For the first staged Agent deployment, Compute makes the existing authenticated Gateway operator route available for node enrollment, and the Sandbox provisions an idle target. Compute configures credential delivery and the intended network and injection policies, then prepares the fresh Harness launch inputs after those policies are ready. Preparation must not start the Harness. The worker authorizes the Agent and its exact source once before activation. The Sandbox starts the Harness during activation; Compute waits for authenticated Harness and workspace-node readiness before publishing user chat and delegated browser routes.

This replaces the earlier requirement for an already-running held launcher, a process instance and startup challenge, an acknowledged placeholder handoff, and a signed release. Replace the six-operation `SandboxDeploymentContract` with three optional operations directly on `SandboxDriver`: `provisionStagedHarness(context)` returns the provisioned target, `prepareStagedHarness(context, projections)` prepares launch inputs, and `activateStagedHarness(context)` starts the Harness. Reuse `applyNetworkPolicy`, `observeNetworkPolicy`, ordinary Harness status, and `cleanup`; a Driver without the required operations does not support staged deployment. Keep one canonical startup state. Already-authorized operations may finish if a grant changes while they run.

OpenShell can activate through a fresh `ExecSandbox` call, which starts the Harness with the installed Provider placeholders without restarting it. `ExecSandbox` selects a Sandbox by Workspace and name; until [upstream issue #5872](https://github.com/ai-openshell/openshell/issues/5872) is resolved, activation can reach a replacement Sandbox with the same name. This temporary risk is accepted. Put a concise TODO beside the activation call. Do not add a second release protocol solely to compensate for that race.

For the first run, OpenShell's executable-descendant matching and substitution that is not restricted to the exact Bearer presentation are also accepted temporarily. The configured effective destination, method, path, Provider custody, source version, and readiness still apply. Full strict-policy qualification remains a 1.0 follow-up.
