# GitHub App credentials through the Credential Proxy

This amendment proposes the GitHub integration for Credential Design 1.0. The OpenClaw Control Plane (OCC) admits the repository grants saved for an Agent. Its selected TokenService issues a usable GitHub App credential, and the selected CredentialProxyDriver configures delivery and the Git-specific network rules. OpenShell enforces the resulting Sandbox policy without exposing the real credential to the Agent. The integration reuses the existing repository editor, admission, grants, compiler, and tests.

## Ownership and execution

OCC admits the Agent's saved `repositoryNetworkPolicy` against the existing Installation ceiling, Namespace repository registrations, and selected repository bindings. It freezes the effective grants in the Agent revision and derives separate `NetworkAccessPolicy` and `CredentialInjectionPolicy` values. Network permission does not by itself authorize credential injection, and an available credential does not grant network access. Do not add another repository allowlist or policy resource.

The selected TokenService owns the GitHub App CredentialSource, App and installation identity, private key custody, issuance, expiry, renewal, and retirement. OCC authorizes Source creation and exact Source use. Source metadata and notifications contain no private key, App JWT, or installation token. The first qualification uses one Agent revision and one Source with a fixed finite repository set and one GitHub permission map. TokenService issues and renews one credential for that Source through the existing Source-only push contract. It does not mint different credentials for different Agents under one Source.

The Agent's finite `github-repository` bindings must select that exact repository set and common permission map. Its saved network grants may cover fewer repositories or grant read where the binding permits write. For example, a credential covering A and B with content-write permission can support saved A-read and B-write grants. OCC checks the binding scope and grants before delivery; the issuer validates the exact finite scope. The Source contract must decide how to establish and verify that fixed scope from the existing selection. Refuse a mismatched binding rather than changing the Source credential implicitly.

Free's current path also issues a distinct token per Agent revision and revokes it independently while peers continue. The Source-shared push contract can deliver the same credential to several Agents, each with narrower network rules and its own Provider association. That can isolate network access and Sandbox withdrawal, but it cannot preserve independent issuer revocation of a shared token. Multi-Agent sharing and its token-revocation guarantee remain an unresolved product and security decision. This amendment neither accepts a weaker guarantee nor introduces a new Source-sharing restriction or admission state. It does not add variants or make contextual issuance a 1.0 dependency.

The canonical OpenShellCredentialProxyDriver owns credential-specific Git network rule generation, Provider association, injection configuration, delivery lifecycle, and readiness. Move or adapt Free Wortley's existing compiler, matcher, and Git-specific overlap checks to that canonical Driver during migration. OCC and the Proxy must reject a candidate when a default, generic addition, sibling rule, or Provider route could bypass the narrower repository grants. Sandbox continues to own the generic baseline. The Proxy can configure an endpointless Provider and apply credential-related rules with `credential_binding.provider` to the target Sandbox through the OpenShell Gateway. Preserve the baseline and use Free's full effective-policy readback to verify the loaded combined rules, their bindings, recipient, and usable credential before readiness or renewal. Coordinate existing policy version and update checks so concurrent changes cannot overwrite or widen the effective policy. The precise Driver handoff requires contract review; no new interface is assumed here.

SandboxDriver owns Sandbox provisioning, containment, and generic network and routing configuration. It does not interpret GitHub issuer identity, CredentialSources, credentials, or credential-specific Git rules. OpenShell physically enforces the complete combined policy. This changes the current [worker credential configuration draft](worker-credential-configuration.md), which assigns complete network-policy application to Sandbox, and the landed Git-aware Sandbox contract. Review and update those contracts before moving implementation.

For push delivery, TokenService notifies the Proxy after committing new material. The Proxy updates the existing delivery resource and acknowledges only when all serving copies can use the resolved version. With no resource, notification succeeds without creating one. An observed delivery failure does not roll back issuance; report a sanitized failure and permit authorized redelivery. Recovery from a notification lost before reaching the Proxy remains separate work under the [delivery contract](installation-credential-ownership.md#configure-delivery).

## Implemented support and remaining work

Free's merged work already provides the [per-Agent editor](https://github.com/openclaw/openclaw-enterprise/pull/6542), [deployment admission and revision snapshot](https://github.com/openclaw/openclaw-enterprise/pull/6543), and [native OpenShell Git rules and Provider binding](https://github.com/openclaw/openclaw-enterprise/pull/6533). A read grant permits Git discovery and upload-pack; write also permits receive-pack. Both discovery operations use `GET /OWNER/REPO.git/info/refs` and differ by the `service` query. The existing compiler matches that query and the HTTP method, but generic `DeploymentRequestPolicy` currently represents only HTTP method and path. The contract follow-up must preserve the service-query match and accepted query forms through admission, compilation, and readback; reject Git delivery if it cannot do so. The compiler cannot enforce a branch or ref restriction. Credential association is at the endpoint; do not assume the HTTP method selects a different Provider.

Native delivery currently requires finite `github-repository` bindings with a common GitHub token permission map. Saved network grants can still permit read on repository A and write on B. [Scoped issue reads](https://github.com/openclaw/openclaw-enterprise/pull/6884) separately permit issue-list and issue-detail GET requests when the Namespace registration and App permissions allow them. Other REST operations, REST writes, and GraphQL are outside that native capability. Stronger ref and draft-PR grants retain their existing supported paths.

The first remaining integration connects the OCC TokenService GitHub App Source and issuer to the new CredentialProxyDriver push path using the existing finite repository selection and saved Agent rules. The [stock OpenShell integration suite](https://github.com/openclaw/openclaw-enterprise/pull/6764) already exercises grants, credential rotation, denial, and downgrade against a controlled Git fixture. It does not qualify the new TokenService-to-Proxy path or prove access to real GitHub.

Full inherited installation-token support comes later. The existing issuer can request the installation's inherited repositories and permissions with an empty access-token request body, but today's inherited `github-installation` binding does not select the native saved-policy delivery path. Adapt the existing owners before enabling that combination; do not claim it is supported by the finite path alone.

## Verification and deferred work

Before qualifying the first integration, create the Source through the authorized API, verify its fixed finite issuance scope and renewal, push it through the selected Proxy, and confirm readiness on the intended Sandbox. Use a credential that covers private repositories A and B, with saved grants allowing only A-read. Through a real Agent and GitHub, fetch a previously absent object from A; deny a fetch from B and a push to A before origin forwarding while the credential remains valid. Reject an overlapping generic GitHub allow and verify the effective loaded policy. Verify rotation, isolation, independent issuer revocation for this qualification case, grant expiry, and the approved withdrawal boundary. `git ls-remote` proves discovery only.

Saving narrower grants changes desired policy; it does not immediately revoke a running native Sandbox. Retain Free's autonomous expiry handling: when an admitted Repo grant or repository session reaches its deadline, retire that exact Sandbox independently of Source token refresh or expiry, and preserve independent revocation of its issued token. A renewed token cannot extend the grant. Confirm retirement of the old Sandbox before reporting withdrawal complete; failed or unconfirmed retirement remains unresolved. Existing protected Git's request-time authorization and stronger ref guarantees remain distinct. Migration and caller switchover require their own qualification and approval; keep the working Git path until then.

After 1.0, review contextual `resolveCredential(source, admittedContext)` and variant renewal, push, and authenticated pull as separate work. Context derives from the admitted consumer and authorized use; repository issuance can derive from the same effective saved grants. OAuth audience or scope restrictions use their own admitted authority. Connection Template repository-policy integration is also deferred. Broader REST, GraphQL, branch/ref enforcement, and full inherited-token delivery require explicit supported semantics and proof.
