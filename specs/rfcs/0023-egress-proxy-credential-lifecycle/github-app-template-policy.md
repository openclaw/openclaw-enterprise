# GitHub App credentials and repository policy

This amendment proposes two independent workstreams. The first integrates an inherited GitHub App installation token with the selected TokenService and per-Agent repository network and credential-injection policy. The second proposes scoped credential issuance when an admitted deployment needs a different provider-issued credential from the same Source. Neither proposal authorizes a Git runtime cutover or changes an existing repository grant.

## Inherited installation token and repository policy

The selected TokenService creates the canonical CredentialSource and retains its GitHub App ID, installation ID, and write-only private key under the current [Source ownership contract](credential-source-ownership.md). OCC authorizes creation and exact Source use, owns IAM and destination policy, and binds the Source by Namespace and ID. Source metadata and update notifications contain no private key, App JWT, or installation token.

Reuse the existing issuer's inherited issuance and response validation: sign an App JWT and submit `{}` to `POST /app/installations/{installation_id}/access_tokens`, without repository or permission overrides. GitHub limits the resulting token to the installation's repositories and granted permissions. TokenService owns issuance, renewal before expiry, rejected or uncertain issuance cleanup, and retirement. The existing Source-only `resolveCredential(sourceInstance, signal)` can return that usable token. Issuer authority does not grant an Agent installation-wide access, and the narrow `github-app-metadata` Source must not be widened.

After TokenService commits new material, it notifies Credential Proxy. Proxy chooses delivery, updates an existing resource even if it has no serving copies, and acknowledges a push only after every serving copy can use the resolved version. With no resource, notification succeeds without resolution or creation. An observed delivery failure does not roll back issuance; OCC reports a sanitized failure and permits authorized manual redelivery. A notification lost before reaching Proxy can leave an older copy appearing ready; detection and automatic recovery remain deferred under the [delivery contract](installation-credential-ownership.md#configure-delivery). A same-owner native provider can renew internally without OCC observing each version.

### Agent repository policy

RepoPolicy is a reusable ceiling of repositories and permitted profiles or operations. An Agent selects RepoPolicy directly, independently of any CredentialSource, Connection Template, or credential binding. The Agent separately selects repositories and profiles or operations within that ceiling. OCC authorizes and admits those selections as the Agent's effective repository policy. GitHub installation coverage and permissions remain an external upper bound on what a selected Source can do; they are not a second OCC repository allowlist. No separate replicated Namespace-wide allowlist is required by this proposal. Exact RepoPolicy resource scope and IAM, and selection among multiple compatible credentials, remain open.

Replacing credential A with B preserves the Agent's RepoPolicy and repository selections. OCC authorizes use of B and validates that B can support those selections. An incompatible Source must be refused without widening or silently rewriting the Agent's grants. Exploring whether RepoPolicy could move into a Connection Template is deferred; this amendment adds no template repository ceiling or duplicate list.

RepoPolicy version, update, and removal semantics require a contract decision. If a shared ceiling is narrowed, OCC must identify affected revisions that still use the old ceiling or start their selected mode's withdrawal process. Do not report the narrower policy as effective for those revisions until its enforcement or withdrawal completes. The protected and native withdrawal guarantees remain distinct.

OCC derives the native Sandbox and credential-injection restrictions from the same effective Agent repository policy that supplies contextual issuance. For native OpenShell, Sandbox owns the repository endpoint rules and explicit Provider credential bindings. Proxy provisions and rotates an endpointless Provider, as specified in the [per-Agent repository network-policy proposal](../20261119-repository-network-policy.md). On the exact HTTPS Git origin and repository path, read permits upload-pack discovery and POST upload-pack. Write adds receive-pack discovery and POST receive-pack. Both discovery requests use `GET /OWNER/REPO.git/info/refs` and differ by the `service` query. Require Git Basic credential presentation, inspected TLS, and enforcement of the complete effective policy, including sibling allows. Deny alternate routes that bypass the repository restriction; treat redirects as new requests.

The current generic deployment request contract has no query field. Stock OpenShell's service matcher also accepts extra query keys and repeated identical values. The reviewed contract must state which query forms are accepted. A method or path subtree does not define GitHub read/write authority. Git-only access does not enable REST, search, discovery APIs, public-repository routes, Actions, administration, merges, or GraphQL. Any REST capability needs separately approved methods and endpoints; PR creation can also require a body check. Denying `/graphql` by default is a candidate, and breaks GraphQL-dependent stock `gh pr` commands.

Existing protected Git continues to require Repo authorization on each new read or write, current binding and pushed-version evidence, and approved-ref checks for receive-pack. A fresh request after committed Repo withdrawal must fail before origin access even while the token is valid; an already authorized request may finish. Qualify binary upload-pack streaming with response-header, byte, first-header, inactivity, and total-exchange limits within session and credential validity. The authorization-reply deadline is separate. Refuse oversized or stalled transfers. Using an internally renewing provider with the existing attempt/material-version authorization interface remains unqualified and requires contract review.

The proposed native mode instead authorizes Git locally and completes withdrawal when old Sandboxes retire. It does not reproduce immediate Repo withdrawal or per-Agent writable-ref checks. Relying on GitHub rulesets for branch protection cannot distinguish Agents that share one App identity. Maintainers must decide whether to approve those different guarantees for a distinct mode. Preserve existing stronger ref and draft-PR grants; do not widen or migrate them implicitly.

## Scoped credential issuance

A normal Source credential can be a static key, an OAuth access token maintained through refresh, or the inherited GitHub installation token above. OAuth scopes established by consent and retained during refresh do not by themselves require deployment context. Context matters when an admitted deployment changes the credential requested from the issuer, such as GitHub `repository_ids` and `permissions`, or a provider-supported OAuth audience or scope reduction.

Use one TokenService interface, `resolveCredential(source, admittedContext)`, returning the canonical `ResolvedCredential`. The issuer determines whether to retrieve, reuse, refresh, or contextually mint usable material. Callers do not select separate `getToken` or `mintToken` operations. The admitted context identifies any issuance restrictions required for that consumer; TokenService must reject restrictions it cannot honor and must not fall back to a broader credential. The existing Source-only operation can support inherited issuance before the contextual Driver amendment ships, so that amendment does not gate the first workstream. The precise signature remains subject to Driver review.

OCC derives and freezes the minimum issuer input from the effective Agent repository policy and admitted deployment after authorizing the deploying principal, Agent, selected RepoPolicy, and exact Source use. An Agent or Proxy request cannot supply its own authority. For GitHub, normalize immutable repository IDs and an explicit permission map; derive App and installation identity from the Source. GitHub applies one permission map to every selected repository, so read access to A and write access to B require distinct variants. Do not union their permissions silently.

TokenService keeps one canonical Source and separate usable material for each admitted issuance scope and isolation boundary. Each variant has its own version, expiry, renewal schedule, refresh status, and authorized push recipients. Proxy delivery resources, resolver callbacks, notifications, retry, and serving-copy evidence must identify that exact variant; Source-only delivery must not overwrite it with inherited material. A Source update or retirement covers its variants. Withdrawal removes the affected recipient and prevents new resolution or delivery for its revoked authority without disrupting peers. Whether equal scopes can share issuance across Agent isolation boundaries requires review; delivery and withdrawal remain attributable to each recipient.

For pull, the draft [OpenShell Gateway assertion proposal](https://github.com/ai-openshell/openshell/pull/5479) authenticates a Sandbox and attached Provider credential to the token endpoint. OCC must validate that assertion and map its identity to a live admitted Agent revision, Source, and authorized issuance scope before resolving a variant. Requested audience or scopes are not authority. Cached credentials do not replace the selected mode's request authorization or withdrawal guarantees. Pull and its version-evidence bridge require separate qualification; neither gates inherited-token push.

## Interface and checkpoints

Propose a reviewed `github-app-installation` Source type with refresh lifecycle, `config.app_id`, `config.installation_id`, and write-only `secret.private_key` through the managed Namespace Source API. TokenService's `createSource` returns the canonical Source; `removeSource` returns removed AccessBindings. OCC retains collection create and exact Source operate checks. RepoPolicy is selected on the Agent, not attached to this Source. The Source schema, RepoPolicy resource and admission contract, Git query and presentation requirements, and contextual resolution and delivery changes require human contract review before implementation.

- **CP7a:** Create the Source through the authorized regular API, verify inherited `{}` issuance, renewal, versioned push notification and delivery failure handling, retirement, and refusal of a mismatched TokenService instance. The issuer's REST request does not grant Agent REST access.
- **CP7b:** Through a regular Agent, fetch a previously absent object from approved private repository A using an installation that also covers disallowed B. Deny a fetch from B and a push to read-only A before forwarding while the token is valid. Replace the Source with a compatible credential and verify that RepoPolicy and selections remain unchanged; refuse an incompatible credential without changing grants. Verify rotation and the approved withdrawal boundary. The protected mode must retain immediate denial after Repo withdrawal; native mode requires separate approval and proof of Sandbox retirement. `git ls-remote` establishes discovery only. Test direct bypass and separately approved REST or GraphQL policy as applicable.
- **Scoped issuance:** Review the Driver amendment independently, then prove distinct issued scopes, per-variant renewal and push recipients, withdrawal without peer disruption, and authenticated pull mapping when supported.
- **RepoPolicy lifecycle:** Narrow a policy shared by two Agents. Verify that revisions still using the old ceiling remain identifiable and that the narrower policy is reported effective only after each affected revision meets its approved withdrawal or enforcement condition.

Keep the working Git path and `bindRepositoryGit` until credential CORE qualifies, the replacement passes its approved real GitHub checkpoints, callers are explicitly cut over, and every retained stronger grant has an equivalent supported path. No runtime behavior or live GitHub proof is established by this amendment.
