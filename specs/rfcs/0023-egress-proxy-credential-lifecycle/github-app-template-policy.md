# Shared GitHub App token and Agent repository grants

This amendment proposes the GitHub integration for Credential Design 1.0. The selected TokenService maintains one shared usable GitHub App token per CredentialSource. The OpenClaw Control Plane (OCC) admits each Agent's saved repository grants as its authorization boundary, and the selected CredentialProxyDriver configures the credential-related rules and injection for that Agent. OpenShell enforces the combined Sandbox policy without exposing the token to the Agent. Different Agents can use the same Source token with different repository grants.

## Ownership and execution

OCC admits the Agent's saved `repositoryNetworkPolicy` against the existing Installation ceiling, Namespace repository registrations, and selected repository bindings. It freezes the effective grants in the Agent revision and derives separate `NetworkAccessPolicy` and `CredentialInjectionPolicy` values. Network permission does not by itself authorize credential injection, and an available credential does not grant network access. Do not add another repository allowlist or policy resource.

The selected TokenService owns the GitHub App CredentialSource, App and installation identity, private key custody, issuance, token expiry, renewal, and retirement. OCC authorizes Source creation and exact Source use. TokenService issues and renews one usable token per Source through the existing Source-only push contract. Source metadata and notifications contain no private key, App JWT, or installation token.

For the first integration with Free Wortley's existing finite `github-repository` path, qualify one Source token with a fixed finite repository set and one GitHub permission map. The existing binding and issuer must agree on that scope; saved Agent grants can cover fewer repositories or grant read where the binding permits write. For example, a token covering A and B with content-write permission can serve one Agent with A-read and another with B-write. OCC admits each Agent's grants separately against the existing ceilings and bindings. The Source contract must establish and verify the finite issuance scope without changing the token implicitly for another Agent. Adapting this existing finite binding to shared Source delivery remains implementation work.

Credential Design 1.0 explicitly forgoes independent upstream GitHub token revocation per Agent. Withdrawing, stopping, or expiring one Agent removes that Agent's binding and network access, or retires its exact Sandbox, without revoking the shared token or disrupting peers. Source rotation updates the token delivered to all Source consumers. Source retirement or upstream revocation affects every consumer of that Source; an operator cannot use Source-wide revocation to withdraw just one Agent.

The canonical OpenShellCredentialProxyDriver owns credential-specific Git network rule generation, Provider association, injection configuration, delivery lifecycle, and readiness. Move or adapt Free Wortley's existing compiler, matcher, and Git-specific overlap checks to that canonical Driver during migration. OCC and the Proxy must reject a candidate when a default, generic addition, sibling rule, or Provider route could bypass the narrower repository grants. Sandbox continues to own the generic baseline. The Proxy can configure an endpointless Provider and apply credential-related rules with `credential_binding.provider` to the target Sandbox through the OpenShell Gateway. Preserve the baseline and use Free's full effective-policy readback to verify the loaded combined rules, their bindings, recipient, and usable credential before reporting readiness or acknowledging refreshed delivery. TokenService issuance and renewal do not depend on a Sandbox or delivery resource. Coordinate existing policy version and update checks so concurrent changes cannot overwrite or widen the effective policy. The precise Driver handoff requires contract review; no new interface is assumed here.

SandboxDriver owns Sandbox provisioning, containment, and generic network and routing configuration. It does not interpret GitHub issuer identity, CredentialSources, credentials, or credential-specific Git rules. OpenShell physically enforces the complete combined policy. This changes the current [worker credential configuration draft](worker-credential-configuration.md), which assigns complete network-policy application to Sandbox, and the landed Git-aware Sandbox contract. Review and update those contracts before moving implementation.

For push delivery, TokenService notifies the Proxy after committing new material. The Proxy updates the existing delivery resource and acknowledges only when all serving copies can use the resolved version. With no resource, notification succeeds without creating one. An observed delivery failure does not roll back issuance; report a sanitized failure and permit authorized redelivery. Recovery from a notification lost before reaching the Proxy remains separate work under the [delivery contract](installation-credential-ownership.md#configure-delivery).

## Implemented support and remaining work

Free's merged work already provides the [per-Agent editor](https://github.com/openclaw/openclaw-enterprise/pull/6542), [deployment admission and revision snapshot](https://github.com/openclaw/openclaw-enterprise/pull/6543), and [native OpenShell Git rules and Provider binding](https://github.com/openclaw/openclaw-enterprise/pull/6533). A read grant permits Git discovery and upload-pack; write also permits receive-pack. Both discovery operations use `GET /OWNER/REPO.git/info/refs` and differ by the `service` query. The existing compiler matches that query and the HTTP method, but generic `DeploymentRequestPolicy` currently represents only HTTP method and path. The contract follow-up must preserve the service-query match and accepted query forms through admission, compilation, and readback; reject Git delivery if it cannot do so. The compiler cannot enforce a branch or ref restriction. Credential association is at the endpoint; do not assume the HTTP method selects a different Provider.

Native delivery currently requires finite `github-repository` bindings with a common GitHub token permission map. Saved network grants can still permit read on repository A and write on B. [Scoped issue reads](https://github.com/openclaw/openclaw-enterprise/pull/6884) separately permit issue-list and issue-detail GET requests when the Namespace registration and App permissions allow them. Other REST operations, REST writes, and GraphQL are outside that native capability. Stronger ref and draft-PR grants retain their existing supported paths.

The first remaining integration connects the OCC TokenService GitHub App Source and issuer to the new CredentialProxyDriver push path, sharing one token across Agents while reusing the existing finite repository selection and saved Agent rules. Free's current path issues and revokes tokens per revision; its [stock OpenShell integration suite](https://github.com/openclaw/openclaw-enterprise/pull/6764) exercises grants, rotation, denial, and downgrade against a controlled Git fixture. It needs adaptation for the shared-token withdrawal semantics and does not qualify the new TokenService-to-Proxy path or prove access to real GitHub.

Full inherited installation-token support comes later. The existing issuer can request the installation's inherited repositories and permissions with an empty access-token request body, but today's inherited `github-installation` binding does not select the native saved-policy delivery path. Adapt the existing owners before enabling that combination; do not claim it is supported by the finite path alone.

## Verification and deferred work

The proposed first qualification uses two real Agents and one Source token covering private repositories A and B. Save A-read for the first Agent and B-write for the second. Confirm that both delivery targets use the same Source version and token, without exposing token material to either Agent. Fetch a previously absent object from A, allow a push to B, and deny cross-repository access and a push to read-only A before origin forwarding while the token remains valid. Reject an overlapping generic GitHub allow and verify the effective loaded policy. Withdraw or expire the first Agent, confirm its access has ended without upstream token revocation, and verify that the second Agent still works with the shared token. Verify Source renewal and rotation across consumers. `git ls-remote` proves discovery only. No live proof is established by this amendment.

Saving narrower grants changes desired policy; it does not immediately revoke a running native Sandbox. Retain Free's autonomous expiry handling: when an admitted Repo grant or repository session reaches its deadline, retire that exact Sandbox independently of Source token refresh or expiry. A renewed token cannot extend the grant, and Agent expiry must not revoke the shared token. Confirm removal of the Agent's effective access or retirement of its old Sandbox before reporting withdrawal complete; failed or unconfirmed withdrawal remains unresolved. Existing protected Git's request-time authorization, per-revision token revocation, and stronger ref guarantees differ from this shared-token mode. Migration and caller switchover require their own qualification and approval; keep the working Git path until then.

Connection Template repository-policy integration and contextual issuance are outside this 1.0 integration. Broader REST, GraphQL, branch/ref enforcement, and full inherited-token delivery require explicit supported semantics and proof.
